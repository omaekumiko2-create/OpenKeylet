# Security

**English** · [简体中文](SECURITY.zh-CN.md)

OpenKeylet is an open-source, local-first autonomous secret vault exposed through local stdio MCP and provided as-is without security warranties. It is **not** a hardened password vault designed to stop a determined local attacker; its goal is to let Agents store, generate, and use credentials automatically and seamlessly while reducing accidental plaintext leaks into model context, API relays, shell history, and public repositories.

## Security goals

- Vault secrets are encrypted at rest with authenticated encryption. Item metadata and the activity log are not, and in the default mode the key is stored on the same machine (see [Local data and backups](#local-data-and-backups)).
- Modules that are not marked `agentVisible` do not return plaintext through `items_search`.
- Hidden values can be used locally by `credential_fill`, `terminal_run`, the managed-terminal tools, `ssh_run`, `ssh_upload`, `ssh_download`, `http_send`, and `secret_write_file`.
- Known stored credentials (the raw value and common encodings: JSON escapes, base64 and base64url including a value embedded in a larger encoding, hex, percent-encoding, shell quoting, and single lines of multi-line values) are redacted from activity errors, terminal output, SSH output, API responses, and browser inspection where OpenKeylet can identify them. Every terminal, SSH, HTTP, and browser result is redacted with the values the MCP session substituted, rendered, generated, ingested, captured, or filled (6+ characters), the current item's hidden values, and the hidden secret values of every enabled item (8+ characters), even when the call names no item. Usernames, contact and address fields, and custom fields whose name and value do not look like a credential (such as `NODE_ENV=production`) are only redacted in calls that use their item.
- OpenKeylet-controlled authentication headers cannot be replaced by the caller; when an item has a saved service URL or website rules, `http_send` sends its secrets only to that destination.

## Explicitly agent-visible values

The per-module **Agent visible** switch is a disclosure decision. When it is enabled, `items_search` includes that module's `value`, and the value may enter the Agent's context and its model provider's logs. For a visible TOTP module, OpenKeylet returns only the current six-digit code, never the permanent TOTP seed.

Do not enable Agent visibility for a value that must remain outside the Agent context. This switch is separate from whether the module may be used by OpenKeylet for fill, SSH, or API actions.

## What OpenKeylet does not protect against

OpenKeylet is not a sandbox, policy engine, DLP system, or authorization server. It does not defend against:

- a malicious, compromised, or prompt-injected Agent (see below);
- another process running as the same operating-system user;
- a compromised browser, extension, terminal, remote host, or operating system;
- an Agent focusing the wrong desktop or browser control;
- sensitive data newly produced by a command or remote service;
- a task whose requested destination or operation is itself unsafe.

Hiding modules from `items_search` and redacting output protect against accidental disclosure in normal use; they are not a boundary against an Agent that is malicious or following prompt-injected instructions. There is no `get_secret` tool, but any enabled item's secret can be substituted into a `terminal_run`, `ssh_run`, or managed-terminal command whose output the Agent controls, sent by `http_send` to any destination when the item has no saved service URL or website rules, or rendered by `secret_write_file` into a file the Agent can then read with its own tools. Output redaction only matches the raw value and the common encodings listed above, so a command that transforms a secret in another way (for example reversing or splitting it) returns it unredacted. The item's **Enabled** switch is the authorization gate: any enabled item can be used by any Agent connected to OpenKeylet.

MCP tool annotations are descriptive hints. OpenKeylet enforces its actual restrictions in the Rust backend and never treats annotations or prompt instructions as authorization.

## Action boundaries

OpenKeylet's MCP tools, in particular `terminal_*`, `ssh_*`, `http_send`, and `secret_write_file`, run with the desktop user's permissions in the OpenKeylet process. They run outside any sandbox or command-approval system that the Agent client applies to its own shell, and `terminal_run` works even when no item is involved. Keep per-tool approval enabled for these tools in the Agent client rather than blanket-allowing the OpenKeylet server.

### Browser and desktop fill

The extension popup uses exact scheme, host and port unless an item has explicit website rules. Multiple-website rules support domain/host/exact/prefix/regex/never matching; ordinary rules retain the saved scheme and port, prefix rules also require the same origin, and regex matching refuses remote HTTP. Rules apply to the focused frame's URL, which is rechecked during injection. Different-origin frames are refused. The popup saves only after an explicit action. It shares the local vault rather than caching passwords in extension storage. A configured owner PIN also protects popup access; each passkey operation confirmed in the extension window verifies it afresh. The bridge pins the extension origin during pairing and requires a pairing token for every WebSocket connection. Page content cannot choose vault RPC methods. Passkey requests completed by a person use a separate extension-origin confirmation window, validate the RP ID against the page origin and public-suffix list, and set the UV flag only after successful PIN verification. Private keys never enter page scripts, extension storage, or Agent-readable fields. Local processes running as the same OS user remain outside this protection boundary.

Agent passkey requests take a different path. **Agent Passkey signing** (System → WEB / 04) is **off by default**, so `browser_passkey` fails until the owner explicitly turns it on. While enabled, `browser_passkey` completes WebAuthn sign-in or registration for an enabled item only when the agent arms the interceptor before triggering the page's WebAuthn request, without opening the confirmation window or asking for the PIN, and the signed authenticator data asserts both user presence (UP) and user verification (UV) on the strength of the owner's standing authorization. `browser_passkey` refuses to take over or resolve a request that is already waiting in a manual confirmation window. The RP ID is still validated against the page origin. Turning the setting off makes `browser_passkey` fail and restores manual-only confirmation.

Optional save suggestions sample visible login fields on a browser-generated form submission after trusted user interaction, not on each keystroke. This is a convenience heuristic, not evidence that a site is trustworthy or that authentication succeeded. Only HTTPS/local pages with the same origin as their top-level tab are eligible. Drafts are bounded to ten tabs and five minutes, held in service-worker memory, and never written to extension storage or sent to an external service. The source URL comes from Chrome's sender metadata. Cross-origin navigation, tab close, bridge disconnection, opt-out, dismissal and explicit extension locking discard drafts. Only a trusted extension page can read them after the configured PIN unlock or commit them with version checks; page messages cannot save or read credentials. The on-page notice carries no captured values. Existing-login comparisons occur locally only while unlocked. Browser/worker restart may discard an unsaved suggestion.

`credential_fill` writes one value to the currently focused control. When the caller sets `submit=true`, OpenKeylet also submits the focused browser form or presses Enter in a desktop or managed-terminal target. Desktop fill depends on the real operating-system foreground focus; background DOM focus is not sufficient. OpenKeylet cannot prove that the focused destination is trustworthy.

### Managed terminal

OpenKeylet remembers the most recently selected compatible project and the current managed terminal within each stdio MCP session. A unique `items_search` result or any explicit item selects the project, allowing later fill, SSH, transfer, HTTP, and terminal actions to omit the repeated name. `terminal_start`, or explicitly using another terminal ID, selects the current terminal so later write, read, fill, and stop calls can omit the repeated UUID. A PTY also keeps its own project binding until it ends. This is conversational convenience state, not an authorization boundary; ended terminals and disabled, deleted, or incompatible projects are ignored automatically.

OpenKeylet does not add a policy shell. `terminal_run` executes an ordinary one-shot local shell command, while `terminal_start` opens the requested program or native Windows script when an interactive process is needed. Children inherit OpenKeylet's normal user environment so installed tools behave as they do for the user. `terminal_run` can write caller-provided text directly to standard input, avoiding shell interpolation and temporary files. It and `terminal_start` can substitute `{{openkeylet:module}}` placeholders in commands or working directories; one-shot stdin, PTY arguments, and later `terminal_write` input support the same local substitution, and `secretEnv` can inject selected modules into a child environment. `terminal_write` may press Enter and `terminal_read` may wait for a requested marker without a OpenKeylet deadline unless the caller supplies one. Those values and common encodings are redacted from returned output. Local commands and ordinary terminal input may affect local or external systems. Redaction covers the values described under Security goals, also when CR/LF, a line editor's wrap, or ANSI escape sequences are interleaved with them, but not unrelated environment variables or every secret a process may print. Managed terminals start with `HISTFILE=/dev/null` and `fish_private_mode=1`, and the default PowerShell is told not to save PSReadLine history, so a command typed with a substituted secret is not written to shell history unless the user's shell profile sets its own history file. `browser_inspect` strips query strings and fragments from listed tabs and masks query values on the inspected page. Every `terminal_run`, `terminal_start`, and `terminal_write` call is recorded in the activity log, including calls that use no item; the record does not include the command or input text.

### SSH

An item with a saved password or private key can grant the Agent full SSH command execution and recursive SFTP file-or-directory transfer. Host, port, and username may be saved as defaults or supplied by the Agent for the current call; port 22 is used when neither source provides a port. `ssh_run` can write caller-provided text directly to the remote process's standard input and substitute `{{openkeylet:module}}` placeholders in that input, its command, or working directory. `secretEnv` can inject additional stored modules into the remote environment. OpenKeylet redacts those values from returned output. Upload and download paths are selected by the Agent for the user's task, and existing destinations are replaced by default after a complete temporary copy has been prepared, including file-to-directory and directory-to-file changes. OpenKeylet has no observation, diagnostic, restricted, or execution mode.

The host key presented on the first connection to a host and port is pinned in a device-local `ssh-known-hosts.json` file in the data directory; it is never synced or exported. Later connections to that host and port must present the same key: a mismatch is refused before any credential is sent, and no MCP tool resets a pin. The owner lists pins with `openkeylet ssh hosts` and resets one with `openkeylet ssh forget-host <host> [--port <port>]`, which asks for the owner PIN when one is configured. Pinning defends against a network attacker impersonating the server; like every file in the data directory, the pin store is protected only by the OS account, so a process or Agent with local shell access can remove pins. First use is still trust-on-first-use (TOFU): the key seen on the first connection is accepted without verification, and because the Agent may supply the host at runtime, it can still direct a credential to a new host, which is then pinned on first use.

### API requests

Any enabled item with a configured secret can be used as an HTTP request context. When an item stores a service URL, the caller may omit the request URL to use it or pass a relative path. A secret from an item that has a saved service URL or website rules, whether injected automatically as authentication or referenced through a `{{openkeylet:module}}` placeholder, a cross-item `{{openkeylet:Item/module}}` placeholder, or `secretBindings`, is sent only to the same Origin as that item's saved URL or to a URL matching one of that item's website rules (when website rules explicitly govern the service URL's own Origin — for example `never`, `exact`, or `prefix` rules — those rules take precedence over the service URL fallback); any other target is refused before anything is sent. An item with no saved URL and no website rules is unbound: the Agent supplies an absolute HTTP/HTTPS URL and so chooses where its secrets go. This binding applies to `http_send` only; placeholders used in `terminal_run`, `ssh_run`, managed-terminal input, and `secret_write_file` are not bound to any destination.

For authentication schemes not covered by the built-in API credential or Basic combinations, placeholders such as `{{openkeylet:password}}` or `{{openkeylet:service token}}` resolve the named module directly and are substituted locally in URL, header, query, JSON/text body, or form values. `http_send.secretBindings` is only an optional alias map when the placeholder name differs from the module. The resolved value is added to response and activity redaction without being returned to the caller; TOTP bindings use the current code rather than the stored seed.

OpenKeylet follows HTTP/HTTPS redirects until the service stops redirecting or the caller's optional timeout is reached; `followRedirects=false` returns the 3xx response instead. On a redirect to a different Origin, OpenKeylet strips the credentials it supplied, and a request body containing a secret is never re-sent to another Origin. The caller may send ordinary headers, cookies, `Host`, or its own authorization values; only headers OpenKeylet injects for the saved credential remain controlled by OpenKeylet. By default `http_send` returns the normal redacted response so API workflows stay fast and seamless; known stored secrets are redacted, while newly minted credentials should be captured via `captureSecrets` (or `holdResponse=true` + `http_save_secret` when the response schema is unknown). When a `captureSecrets` path misses or the body is not JSON, the body and headers are withheld in an encrypted local receipt (up to 1 MiB, 8 receipts / 5 minutes per session) and `responseId`, numbered `candidates`, and `jsonPaths` are returned so `http_save_secret` can save the key without repeating a one-time request. Similarly, `browser_save_key` and `browser_save_login` let the paired extension save a displayed API key or submitted login straight into the vault without exposing plaintext in MCP output. Activity records include the HTTP method, Origin, and path without the query string. Known stored secrets are redacted before the activity is saved.

`http_send` can upload local files or save a response to a local file when the caller supplies a path. OpenKeylet does not independently decide whether a user-requested local file is appropriate to send, which HTTP/HTTPS destination should receive it, or where an explicitly requested response should be stored. Existing response files are replaced by default; the caller can explicitly disable replacement.

## Local data and backups

The vault (`vault.json`) remains in the current user's application-data directory (`…/mcp-vault/v2`). In the default mode, the 256-bit vault key is kept outside the data directory: in the operating-system credential store (Windows Credential Manager or Linux Secret Service) when available, or in a separate per-user key file (`~/.config/openkeylet/master.key` on Linux/Unix, `%LOCALAPPDATA%\OpenKeylet\master.key` on Windows, `~/Library/Application Support/OpenKeylet/master.key` on macOS). Key files and newly created key directories are restricted to the current user (`0600`/`0700` on Unix; protected owner+`SYSTEM` NTFS DACL with inheritance disabled on Windows). Existing legacy `<data_dir>/master.key` files are moved out conservatively on open after verifying decryption against `vault.json`, and the legacy path remains a permanent read fallback. When an explicit data directory is set (`OPENKEYLET_DATA_DIR`), the key stays self-contained at `<data_dir>/master.key`; setting `OPENKEYLET_KEY_FILE` to an absolute path overrides both the default file location and the OS credential store in any mode. Because the default mode keeps the key outside the data directory, copying the data directory alone is no longer a complete backup — use passphrase-protected `.mvault` export or repository sync instead. At-rest confidentiality still rests on the OS account and full-disk encryption: anyone who can read both the data directory and that account's credential store or key directory can decrypt the vault.

Only each item's secrets bundle (passwords, usernames, private keys, tokens, TOTP seeds, passkeys, card, identity, and secure-note fields, password history, and agent notes) is encrypted. Item names, descriptions, folders, hosts, ports, service URLs, website rules, and custom field names are stored unencrypted in `vault.json`, and the activity log is stored unencrypted in a separate device-local `activity.jsonl` file in the data directory that is never uploaded or exported.

PIN protects GUI plaintext viewing and extension vault access, and verifies each passkey operation confirmed in the extension window. It is not a separate encryption key and does not stop another process running as the same user.

New desktop and CLI (`--passphrase`) `.mvault` exports use a separate user password (≥12 characters), a random 128-bit salt, Argon2id (64 MiB, 3 iterations, 1 lane), and XChaCha20-Poly1305 with version-bound associated data. No password or unlock key is included in the file. An incorrect password does not modify the local vault. Legacy and non-passphrase CLI automatically unlocked packages still include their unlock material and must be protected like plaintext secrets. Both containers remain importable.

### Remote Browser Bridge & Headless Management

Browser Bridge binds only to `127.0.0.1` by default. Non-loopback binding (`OPENKEYLET_BRIDGE_BIND`) is refused unless explicitly enabled with `OPENKEYLET_BRIDGE_ALLOW_LAN=1`, and supports optional client IP/CIDR allowlists (`OPENKEYLET_BRIDGE_ALLOW_IPS`), configurable extension origins (`OPENKEYLET_BRIDGE_ALLOWED_ORIGINS`), connection metadata logging (without credential values), connected-client tracking, and pairing token rotation (`openkeylet browser reset`). Internal `/internal/*` endpoints reject non-local peers even in LAN mode.

The optional headless management server (`openkeylet admin serve`) is disabled by default, binds strictly to `127.0.0.1:39273` for SSH tunnel access (`ssh -L 39273:127.0.0.1:39273 user@server`), requires a fresh 256-bit Bearer token with rotation and revocation endpoints, hides secret plaintext by default, and requires Owner PIN verification for explicit reveals when a PIN is configured. See [docs/HEADLESS_AND_REMOTE.md](docs/HEADLESS_AND_REMOTE.md).

Card, identity and secure-note fields use the existing encrypted secret envelope and default to hidden from agents. These fields alone do not enable generic SSH/HTTP/agent-fill capabilities. Browser access requires an unlocked session and a user-selected operation. Autofill checks the current origin, allows only HTTPS or local development addresses, skips hidden fields and never submits forms.

Deleted items remain encrypted in the local trash until explicitly purged, and cannot be resolved by agent operations, autofill or passkey signing. The latest 20 previous passwords are encrypted inside each item's secret envelope; only unlocked owner history commands can return them. History values are also included in known-secret redaction. Trash restore/purge and history clearing require current revision tokens. Full exports and GitHub snapshots retain trash and history; deleting locally does not erase previous backups.

## Optional GitHub snapshots

GitHub backup uses a separate authenticated-encryption format, not the self-unlocking `.mvault` container. A random 256-bit sync key encrypts the entire portable payload with XChaCha20-Poly1305 and version-specific associated data. By default that key is stored in a second private repository of the same account, named after the vault repository plus `-key`, so that binding the account is enough to restore on another device and no single repository holds both the ciphertext and its key. This separation covers the leak of one repository: one made public, forked, cloned, or reachable by a token scoped to it. It is not protection against whoever controls the account, a token that can read both repositories, or the hosting provider; any of them can read the vault. A key the owner supplies when connecting an existing backup is used instead and is not uploaded. The repository access token is never uploaded. Binding a repository does not change how the local vault is encrypted or unlocked: the device keeps the sync key and access token in `github-backup.json`, encrypted with the local vault key. Serialized local secret buffers are zeroized after use.

Account checks inspect only owned `private: true` repositories (verifying the `openkeylet-vault` topic or `openkeylet.vault.json` envelope header without decrypting) to discover existing vault repositories automatically. When explicitly selected, local GitHub CLI authorization is read through a hidden, bounded subprocess with a timeout; the token is not returned to the renderer. Repository creation is limited to the authenticated user's account and always requests private visibility; the key repository is created when it is missing, the vault repository only when the owner asks. Existing repositories are never renamed or made private automatically. First upload is an explicit setup option and uses the same encrypted snapshot and conflict checks as later uploads.

The client talks only to GitHub.com's API or, for a self-hosted Gitea / Forgejo connection, to the HTTPS server the owner configured; it refuses redirects, bounds response/snapshot sizes, and does not echo remote error bodies. It checks the vault repository's identity, default branch, and private visibility before uploads, syncs, restores, and history reads, and also verifies that a paired key repository has not been turned public before continuing. Updates use the previously acknowledged blob SHA; conflicting or uncertain writes are never force-retried. These checks do not stop the repository owner from later making a repository public, deleting it, or changing it between API calls. Authentication protects snapshot contents, not availability or rollback: the current manual backup format does not provide cryptographic freshness guarantees against a malicious repository operator.

Recovery imports merge into the vault transactionally, without deleting or overwriting local items. Git history retains past ciphertext. Disconnecting does not erase remote backups, remove other clones, revoke the token, or rotate the sync key. Anyone with the sync key and any snapshot can decrypt that snapshot, and Git history keeps both. A compromised local user account remains outside the security boundary. Deleting the key repository leaves the snapshots unreadable unless a connected device or an offline copy of the key remains; OpenKeylet cannot reset the key.

## Signed GitHub Releases updates

OpenKeylet checks for updates via the fixed GitHub Releases manifest URL (`https://github.com/omaekumiko2-create/OpenKeylet/releases/latest/download/latest.json`) with no custom server or third-party domain. Official release builds embed a 32-byte Ed25519 public key at compile time and require a valid Ed25519 signature over the domain-separated manifest payload (`openkeylet-update-v1\n<payload>`), exact byte size and SHA-256 verification of the downloaded archive, HTTPS GitHub Releases host allowlisting (including redirects), SemVer downgrade protection, safe archive path validation (blocking traversal and links), and macOS `codesign --verify --deep --strict` verification before replacing application files. Local builds without an embedded release public key never auto-install updates. Installing updates or changing update preferences requires an unlocked owner session when PIN lock is configured.

## Reporting a vulnerability

Report suspected vulnerabilities privately through GitHub Security Advisories. Do not include real credentials, vault files, backups, master-key files, API responses, terminal output, or sensitive local paths.
